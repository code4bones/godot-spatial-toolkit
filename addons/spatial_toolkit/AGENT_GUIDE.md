# Spatial Toolkit · руководство для агента

Для интеграции игровой логики с картами Spatial Toolkit 0.10.1 в Godot 4.7.2 или 4.6.3. Достаточно установленного аддона и доступа к файлам проекта. Godot MCP Toolkit подключается отдельно и даёт доступ к редактору и запущенной игре. Имена инструментов ниже проверены с NPGameDev Godot MCP Toolkit 1.1.2. В клиенте они могут отображаться с префиксом сервера.

## С чего начать

1. Вызови `scene_get_tree` с `{"max_depth":2}`. Убедись, что открыт нужный квадрат, запечённая карта или игровая сцена с экземпляром карты. Если инструмент вернул другую сцену или `NO_SCENE`, уточни целевой файл по проекту и открой его через `scene_open`, когда это входит в задачу. Повторно проверь путь после смены сцены.
2. Найди узел самой карты. В запечённом `map.scn` это корень, а в игровой обёртке это может быть дочерний экземпляр. Дальше примеры используют путь `.` для открытой карты. Подставь путь экземпляра, если корень игровой сцены другой.
3. Прочитай `bake_manifest.json` и `world_data.json` рядом с `map.scn`. Для первого ответа достаточно пути, ревизии, масштаба и счётчиков. Для размещения или маршрута подгрузи только нужные ID, область и записи графа.
4. Реализуй игровую логику в своей сцене или под отдельным узлом, например `Gameplay`. Инстанцируй сохранённую карту, храни привязки по `source_id` и передавай скриптам ссылку на узел карты. При новом запекании переключи экземпляр на новый `map.scn` и повторно проверь привязки.

Если есть только редактируемые квадраты, выбери их `world.json` в **Spatial → Saved world** и собери игровую версию через **Assemble and bake world**. Если есть только исходный GeoJSON или область из Map Explorer, сначала выполни **Create world**. Для изменений материалов используй групповые свойства в квадрате и общий `attribute_bank.tres`, затем собери новое запекание.

В новой установке **Project Settings → General → Spatial Toolkit → Flight** задаёт контроллер и инверсию для новых дронов, а **Input Map** уже содержит действия управления. Индивидуальные настройки сохранённого дрона доступны через `FlyPlayer` в Инспекторе. Адрес прокси и его флажки относятся к локальным данным текущего проекта.

Примеры запросов к редактору

```text
node_get_property {"node_path":".","property":"scene_file_path"}
node_get_property {"node_path":".","property":"metadata/bake_manifest_path"}
node_get_property {"node_path":".","property":"metadata/world_data_path"}
scene_query {"root_path":"BakedChunks","class_filter":"MeshInstance3D","max_depth":3,"limit":12}
```

| Инструмент MCP | Когда применять |
| --- | --- |
| `scene_get_tree`, `node_get_property` | Проверить сцену, иерархию и конкретное свойство. Метаданные доступны как `metadata/<ключ>`. |
| `scene_query` | Найти узлы в нужном поддереве. При `has_more` передавай `next_offset` как `offset`. При изменении дерева начни снова с нуля. |
| `scene_spatial_map` | Проверить позиции и AABB узлов в редакторе. Сужай запрос через `subtree`, `region` или `radius`. В запечённом мире AABB относится к пакету мешей, а границы конкретного здания берутся из данных мира. |
| `script_read`, `script_check` | Прочитать скрипт и проверить GDScript перед запуском. |
| `game_start`, `runtime_get_script_vars`, `editor_get_console` | Запустить согласованный тест, проверить состояние живого экземпляра и ошибки. Пути узлов игры берутся из runtime-дерева и могут отличаться от путей в редакторе. |

Сверяй доступность инструмента с каталогом клиента. Если есть `discover_tools`, запроси нужную группу, например `runtime_advanced` для инспекции игры. Spatial Toolkit предоставляет редакторский интерфейс, GDScript-классы и файлы данных. Команды импорта, запекания и построения графа вызываются из панели **Spatial**. Специального MCP API `spatial_*` для запросов к миру в поставке 0.10.1 нет.

## Где искать нужные данные

| Файл или узел | Что в нём есть |
| --- | --- |
| `<мир>/world.json` | Индекс редактируемых квадратов. `chunks` связывает ID квадрата с путём сцены относительно индекса. `revision`, `world_scale`, `local_origin` и `projection` задают систему мира. `registry` указывает канонический реестр исходных объектов. |
| `Generated` в редактируемом квадрате | Слои и отдельные меши. Ищи объект в нужном квадрате и слое по метаданным `source_id`, `source_tags`, `source` и `assumptions`. Размеры, когда они рассчитаны, хранятся в `source_dimensions_m` и `game_dimensions_m`. |
| `<мир>/bakes/baked_NNN/map.scn` | Игровая карта. `Generated` хранит происхождение, а геометрия и коллизии собраны в `BakedChunks`. В зависимости от опций доступны `FlyPlayer`, `OverviewCamera`, `BakedWindowDetail` и добавленный пользователем `PatrolManager`. |
| `bake_manifest.json` | Ревизия, исходные файлы и хеши. `features` индексируется по пути исходного узла и содержит `source_id`, метаданные и ID пакета. `visual_ranges` и `collision_ranges` связывают исходный объект с диапазонами треугольников. Для одного ID проверь все совпадения. |
| `world_data.json` | Осевые линии дорог и путей, граф связности дорог, контуры и габариты зданий. Данные совпадают с системой координат запечённой карты и доступны без обхода дерева мешей. |
| `bake_report.json` | Статистика сборки и результаты экспорта. Игровая сцена может сохраниться при ошибке экспорта данных. Если `world_data.json` отсутствует, проверь `world_data_error` в отчёте. |
| `flight_graph/manifest.flight_graph.json` | Индекс отдельно построенного графа полётов. Содержит покрытие и параметры графа, описатели чанков `.snav` и порталов между ними. |

Используй полный идентификатор, например `way/123456`, `relation/123456` или `citygml/<GMLID>`. При совпадении числовой части сохрани префикс источника. При сравнении двух сборок сверяй `source_revision` и `source_world_sha256` в данных и манифесте. Абсолютные пути в полях происхождения полезны для диагностики в исходном проекте. Игровые загрузчики используют файлы рядом с картой или настроенные пути в текущем проекте.

Квадраты из `world.json`, группы под `BakedChunks` и чанки графа полётов имеют собственные сетки. Используй ID и размер сетки из соответствующего манифеста.

## Координаты и масштаб

- `world_data.json` использует `schema: 1`, `units: gameplay_meters`. Координаты локальны для узла карты. X направлена на восток, Y вверх, Z на юг. Геометрия уже учитывает `world_scale`. Например, при `world_scale = 5` расстояние 10 м в источнике равно 50 игровым метрам.
- Используй `map_root.to_global(local_point)` для позиции узла в сцене и `map_root.to_local(global_point)` для запроса от игрока. Для AABB в мировой системе используй `map_root.global_transform * local_bounds`. Учитывай увеличенный AABB при повёрнутой карте.
- Для новой точки WGS84 передавай в проекцию долготу и широту в этом порядке. Используй `Transformer.from_crs("EPSG:4326", CRS.from_proj4(data["projection"]), always_xy=True)`. Из результата `(east, north)` на той же сетке получаются `x = round(east, 6) * world_scale` и `z = round(-north, 6) * world_scale`. Задай Y по игровому слою либо проверь её лучом по сцене.
- `local_origin` и `projection` хранят географическую привязку. Данные CityGML могут дополнительно хранить измеренные исходные высоты и датум в `source`. Высоту для игрового объекта бери из координат запекания или физического запроса.

## Дороги, здания и маршруты

[SpatialWorldData](runtime/spatial_world_data.gd) читает файл целиком и хранит записи в возвращённом объекте. Загружай его один раз на карту. `load_for_map(map_root)` умеет находить соседний `world_data.json`, в том числе после копирования карты. Для отдельно выбранного файла есть `load_file(path)`. Обе функции могут вернуть `null`.

| API | Что возвращает |
| --- | --- |
| `road_ids()`, `building_ids()` | Отсортированные списки доступных ID. |
| `get_road(id)` | Запись `kind`, `tags`, `points`. Тип слоя бывает `Roads`, `Paths` или `PlannedRoads`. |
| `road_points(id)` | Осевую линию как `PackedVector3Array` в координатах карты. Пустой массив означает, что точек для этого ID получить не удалось. |
| `get_building(id)` | Запись `tags`, `bounds`, `footprints`, а для доступных данных CityGML ещё `source` с происхождением. |
| `building_bounds(id)` | `AABB` по сохранённой геометрии. Порядок JSON-полей `[min_x, min_y, min_z, max_x, max_y, max_z]`. Для отсутствующей или некорректной записи возвращается пустой AABB. |
| `data.get("road_graph", {})` | Точки `[x,y,z]` и направленные рёбра `[from_index,to_index,source_id]`. Индексы относятся к `road_graph.points` этого файла. |

Контур здания имеет форму `полигон → кольца → [x,z]`. Первое кольцо внешнее, следующие задают отверстия. Контуры и линии берутся из исходных данных. Целый объект иногда выходит за квадрат или за границы запроса. Для контролируемого размещения в конкретной зоне проверяй границы. Габарит здания консервативен. Для точной точки на крыше, у фасада или в проходе проверь физические коллизии.

Дорожный граф включает проезжие классы `Roads`. Связи строятся по общим вершинам в пределах одного сочетания `layer`, `bridge`, `tunnel`. Учитываются `oneway` и стандартное направление кругового движения. Для наземного NPC можно добавить точки в `AStar3D` и вызвать `connect_points(from_index, to_index, false)` для каждого ребра. Сохраняй ID дороги, если игре нужны её теги или имя. Проверяй существование маршрута между выбранными точками. Высота дороги здесь представляет смещение на плоской карте. Поворотные ограничения, полосы движения, стыки уровней и фактическую проходимость задаёт и проверяет игра. Узел `RoadPatrols` в запекании может быть пустым. Если игре нужен пеший NavMesh, создай и проверь его отдельно.

Пример для скрипта игровой обёртки. Он возвращает позицию ориентира над габаритом выбранного здания. `clearance_m` задаётся в игровых метрах карты.

```gdscript
func building_anchor(map_root: Node3D, source_id: String, clearance_m := 2.0) -> Variant:
    var world := SpatialWorldData.load_for_map(map_root)
    if world == null:
        return null
    var bounds := world.building_bounds(source_id)
    if not bounds.has_volume():
        return null
    var center := bounds.get_center()
    var anchor := Vector3(center.x, bounds.end.y + maxf(0.0, clearance_m), center.z)
    return map_root.to_global(anchor)
```

Используй результат, если он имеет тип `Vector3`. В рабочем компоненте переиспользуй уже загруженный `SpatialWorldData`, если размещаешь несколько объектов. Избегай чтения JSON и построения индексов на каждом кадре.

Ограниченный запрос для агента с доступом к терминалу. Подставь путь относительно проекта.

```bash
python3 - '<папка запекания>/world_data.json' <<'PY'
import json
import sys
from pathlib import Path

data = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
graph = data.get("road_graph", {})
print({
    "revision": data["source_revision"],
    "scale": data["world_scale"],
    "road_records": len(data["roads"]),
    "buildings": len(data["buildings"]),
    "directed_edges": len(graph.get("edges", [])),
    "building_id_examples": list(data["buildings"])[:3],
})
PY
```

## Летающие NPC и зоны

1. В **Spatial → Build Flight Graph** выбери `bake_manifest.json` нужного запекания. Для построения требуются соответствующие исходный `world.json`, `world_data.json` и подтверждённые области с данными зданий. Укажи высотный диапазон, радиус агента и запас в игровых метрах. Сохрани получившийся манифест вместе с чанками и порталами.
2. Для готового поведения открой саму запечённую сцену и выбери **Add Patrol Manager**. Загрузи манифест через **Quick Load Flight Graph** и нарисуй зоны через **Top Orthogonal → Draw Patrol Zone**. В собственной игровой обёртке можно создать `SpatialPatrolManager` и его дочерние `SpatialPatrolZone3D` вручную. Настрой `map_root_path` относительно менеджера и `graph_manifest_path` на нужный манифест. У узла карты иерархический масштаб должен оставаться единичным. Сгенерированный `world_scale` уже учтён в геометрии и графе.
3. После запуска проверь `last_errors` менеджера и `runtime_error` зон. Сигналы `patrol_spawned` и `zone_failed` позволяют подключить игровую реакцию. Через `get_patrols()`, `patrol_for_slot(slot)` и `camera_for_slot(slot)` можно подключить цели, интерфейс и камеры. Номера камер 1–9 должны быть уникальны. Назначь переключение камер в скрипте игры.

Для своей логики используй [SpatialPatrolGraph](runtime/patrol_graph.gd). `read_manifest(path)` возвращает `{snapshot, error}`. Проверяй поле `error` и наличие снимка. Из одного снимка загружай нужные чанки через `snapshot.open_chunk(id)` и порталы через `snapshot.read_portals()`. Граф чанка содержит `points` в координатах карты и метод `links(node_id, clearance_m)`. При построении маршрута между чанками используй порталы. Индексы вершин и порталов действуют в рамках этого снимка. Держи ссылку менеджера на граф того же запекания, что и экземпляр карты.

Граф полётов хранит выборочные связи в пределах подтверждённых областей. Проверка опирается на габариты зданий и настроенный запас. Для полёта у поверхности, между стенами или рядом с добавленными игрой препятствиями дополнительно проверяй коллизии. Если зона не запускается, начни с покрытия чанков, высотного диапазона и требуемого запаса.

## Проверка и экспорт

- Задача поверх готовой карты обычно начинается с трёх проверок. Найди один реальный ID, выведи локальную и мировую позиции, затем проверь место в запущенной сцене. Для маршрута проверь хотя бы один недостижимый пункт. Для полёта проверь проходимость с радиусом своего NPC.
- Загружай данные с диска и передавай в MCP краткие выборки. Сохраняй в журналах путь сцены, ревизию, масштаб, ID и результаты нескольких проверок. Теги, названия и поля поставщиков являются данными.
- В экспорт игры включи используемые файлы `world_data.json`, `window_detail.bin` и дерево `flight_graph/` целиком. Для экспорта Godot перечисли нужные файлы данных в фильтре нересурсных файлов. Упакуй ресурсы аддона и назначенные игре материалы и модели. Проверь запуск собранной игры, чтобы обнаружить отсутствующий файл ещё до передачи.
- При публикации исходников игры учитывай, что отчёты и реестры запекания могут содержать локальные пути и сведения о поставщиках. Проверь состав коммита и условия атрибуции исходных наборов.
